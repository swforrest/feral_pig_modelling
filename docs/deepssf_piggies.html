Abstract

Here we show an example of how to use the functions in the deepSSF package, showing data loading, model training and testing and generating simulations.

To install and use the package, visit the GitHub repository here: https://github.com/swforrest/deepSSF_package, which has instructions in the README. This script will not download with the package, but it can be accessed from the deepSSF_package repo, under the ‘examples’ folder (as a Jupyter notebook or a html file).

We use data that comes with the package in the datasets folder, which is the GPS tracking data of a single water buffalo (~10,000 locations), and two spatial layers, NDVI (the average from 2018-2019, which covers the temporal extent of the data), and slope.

Import data

The csv file is imported with a timestamp and an x and y coordinate. In our case the data was already in a projected format that is specific to Australia (EPSG:3112), which is the same crs as the raster data which will be imported.

print(f"Individuals   : {raw_df['name'].nunique()}")

# tz-aware Darwin column would be converted straight back to UTC and hour_t1 would

raw_df["t1_"] = (
        pd.to_datetime(raw_df["t1_"], utc=True)
        .dt.tz_convert("Australia/Darwin")
        .dt.tz_localize(None)

load_environmental_layers()

Reads each GeoTIFF listed in LAYER_PATHS, min–max

  • Scales every band to [0, 1], and returns:
    • env_layers — dict mapping layer name → NumPy array: 2-D (H × W) for single-band GeoTIFFs, 3-D (bands × H × W) for multi-band ones, where each band becomes its own model input channel
    • raster_transform — Affine object that converts pixel (row, col) indices to the projected coordinates (easting, northing) of the raster(s), which should be in the same CRS as the GPS data. This transform is used whenever we need to translate between pixel space and real-world coordinates.

Two things to watch for:

  1. The keys 's2' and 's2_dir' are reserved for the monthly Sentinel-2 composite loader — a single GeoTIFF passed under the name 's2' is silently skipped (see the note in the paths cell above).
  2. The rescaling uses a single global min/max across all bands of a file, and computes (data - lo) / hi rather than (data - lo) / (hi - lo). Our index raster is int16 scaled by 10 000 with ±10 000 fill values, so the loaded values span [0, 2] rather than [0, 1] and the three indices are not individually normalised. That is workable (the CNN can rescale internally) but if it hurts training, pre-scale each band yourself and save as .npy — non-.tif paths in LAYER_PATHS are loaded with np.load(..., mmap_mode='r') and left untouched, though at least one real .tif must remain in the dict so the transform can be set.
Code 
env_layers, raster_transform = load_environmental_layers(LAYER_PATHS)
print("Layers loaded:", list(env_layers.keys()))
for name, arr in env_layers.items():
    print(f"  {name}: shape={arr.shape}, min={arr.min():.3f}, max={arr.max():.3f}")

# Each band of a multi-band layer becomes one CNN input channel, so count bands
# (not layers) here and reuse the total when setting ModelParams below.  Deriving
# it means switching rasters in LAYER_PATHS needs no other edits.
N_SPATIAL_CHANNELS = sum(1 if arr.ndim == 2 else arr.shape[0] for arr in env_layers.values())
print(f"Spatial channels: {N_SPATIAL_CHANNELS}")

prepare_movement_df()

Converts a fixes dataframe (one row per GPS location) into a step dataframe (one row per movement between consecutive fixes).

  • For each step it computes:
    • dx, dy — displacement in projected CRS units (metres)
    • bearing — direction of travel (radians; 0 = north, clockwise positive)
    • bearing_tm1 — bearing of the previous step, used as a model input so the network can capture directional persistence by estimating a turning angle
    • dt_hour — time elapsed between consecutive fixes (hours)
    • hour_t1, yday_t1 — decimal hour-of-day and day-of-year at the step start location
    • *_sin1 / *_cos1 — sine/cosine encodings of hour and yday (see SCALAR_COLS below)

The trailing underscore on column names (x1_, y1_, t1_, etc.) flags them as “start of step” variables; x2_, y2_, t2_ are the corresponding “end of step” values, following the convention of the amt package (Signer et al. 2019). The last fix for each individual is dropped because no forward step can be formed.

Code 
# The CSV is already in amt step format, but prepare_movement_df() expects one row
# per *fix* and rebuilds the steps itself (it also derives bearing, dt_hour and the
# cyclic time encodings the model needs).  Point it at the step-start columns and
# let it re-form the steps from consecutive fixes.
step_df = prepare_movement_df(
    raw_df, 
    id_col="name", 
    time_col="t1_", 
    x_col="x1_", 
    y_col="y1_"
)
n_dropped = len(raw_df) - len(step_df)
print(f"Movement steps : {len(step_df):,}  ({n_dropped} dropped — last per individual)")

SCALAR_COLS

These are non-spatial inputs. For processing with convolutional layers, they are converted into spatial windows (rasters/arrays), and stacked with the truly spatial covariates.

The model receives a fixed-size spatial window centred on each step’s start location. To let the network express time-varying habitat preferences (e.g. different nocturnal vs diurnal use), scalar covariates are tiled into additional channels of the same H × W size, so every pixel “knows” the current time context when habitat suitability is estimated.

  • hour_t1_sin1 / hour_t1_cos1
    • Sine and cosine of (2π × hour / 24), encoding time-of-day as a circular variable. The circular encoding means 23:00 and 01:00 are treated as adjacent — a plain hour value would have an artificial discontinuity at midnight.
  • yday_t1_sin1 / yday_t1_cos1
    • Same circular encoding for day-of-year (1–365), capturing seasonal variation in habitat use (e.g. dry-season vs wet-season movements).
  • dt_hour
    • Elapsed time between consecutive fixes (hours). Because GPS collars do not always fix at a perfectly regular rate, including dt_hour lets the movement kernel rescale expected displacement proportionally to the actual time interval rather than assuming a fixed fix rate. Note: dt_hour must be supplied at simulation time as well, so that simulate_trajectory() produces inputs consistent with training.
Code 
SCALAR_COLS = ["hour_t1_sin1",

WINDOW_SIZE

The size of the local availability window in cells/pixels; 101 pixels × 20 m = 2020 m across, i.e. 1010 m from the centre location to the edge

Code 
WINDOW_SIZE = 51

PIXEL_SIZE

Raster resolution in CRS units (metres here). Read straight off raster_transform rather than typed in: the transform is the authority on the grid the model is trained against, and a hand-entered value that disagrees with it silently mis-scales the movement kernel — which is parameterised in metres — against a grid measured in pixels.

Code 
# transform.a is the cell width, transform.e the (negative) cell height
PIXEL_SIZE = abs(raster_transform.a)

if not math.isclose(abs(raster_transform.a), abs(raster_transform.e)):
    raise ValueError(
        f"Non-square pixels ({abs(raster_transform.a)} x {abs(raster_transform.e)}); "
        "the model assumes square cells."
    )
print(f"Pixel size: {PIXEL_SIZE} m  →  window {WINDOW_SIZE} px = "
      f"{WINDOW_SIZE * PIXEL_SIZE:,.0f} m across")

BATCH_SIZE

Number of training samples (movement steps) per training mini-batch

Code 
BATCH_SIZE  = 512

N_CONV_LAYERS_MOVE

How many convolutional layers in the movement subnetwork of the model?

Each of the convolution layers has a max pooling layer, so more layers will result in greater dimension reduction that will feed into the fully-connected layer that outputs the movement parameters.

Code 
N_CONV_LAYERS_MOVE = 3

N_CONV_LAYERS_HAB

How many convolutional layers in the habitat selection subnetwork of the model?

These convolution layers do not have max pooling layers, so there is no dimension reduction. More layers will increase the depth of the model and allow for more abstracted features to be identified, but will slow model training/prediction.

This count includes the final convolution layer, which is the one that collapses the feature maps down to the single-channel habitat selection surface, so the minimum is 1.

Code 
N_CONV_LAYERS_HAB = 4

OUTPUT_CHANNELS

Number of convolutional filters (and therefore feature maps) for each convolution layer. More convolutional filters can provide more flexible functions, but will increase the number of parameters and slow down training times.

Code 
OUTPUT_CHANNELS = 8

Pre-calculate the flattened CNN output size

This value will be the input to the fully-connected layers in the movement subnetwork, and is calculated here so that ModelParams can be set without hard-coding it.

flattened_conv_dim() reproduces exactly what the layers inside ConvJointModel do to the spatial dimensions: * conv (padding=1) keeps the spatial dimension unchanged at each layer * maxpool k=2, s=2 halves the spatial dimension (floor division) at each layer

Because every movement conv layer is paired with a max pooling layer, this size depends on N_CONV_LAYERS_MOVE — so it has to be recalculated whenever that (or WINDOW_SIZE, or OUTPUT_CHANNELS) changes. It raises an error if the window is pooled away to nothing, which means too many layers for the window size.

Code 
DENSE_DIM = flattened_conv_dim(
    image_dim=WINDOW_SIZE,
    n_conv_layers_move=N_CONV_LAYERS_MOVE,
    output_channels=OUTPUT_CHANNELS,
)
print(f"After {N_CONV_LAYERS_MOVE}x conv+maxpool: dense_dim_in_all={DENSE_DIM}")

Removes steps whose straight-line displacement exceeds half the spatial window (WINDOW_SIZE × PIXEL_SIZE / 2 metres). Such steps would place the true next location outside the predicted probability map, causing an index error in the loss function.

print(f"Steps after window filter: {len(step_df):,}")

make_dataloaders()

Splits step_df into train / val / test subsets (here 80 / 10 / 10 %) and returns a PyTorch DataLoader for each.

The split is a torch.utils.data.random_split, not a chronological one — each subset is a random sample of steps drawn from across the whole dataset and all 28 individuals. Consecutive steps are highly autocorrelated, so a random split leaks information between train and test and will make the validation numbers below look better than genuine out-of-sample performance. If you want an honest held-out estimate, split step_df yourself (by individual, or by time) and build the DataLoaders from the resulting subsets.

  • Each DataLoader yields tuples of:
    • x1 — spatial window tensor (batch × n_spatial_channels × H × W)
      • One channel per raster band in LAYER_PATHS, cropped around each step’s start pixel.
    • x2 — scalar covariate tensor (batch × len(SCALAR_COLS))
      • Raw scalar values; broadcast into spatial maps inside the model.
    • x3 — previous bearing tensor (batch × 1)
      • Conditions the movement kernel on the direction of the prior step.
    • (px2, py2) — pixel indices of the true next location within the window
      • Used by the loss function to look up the predicted probability at the observed destination.

The layer_paths argument causes the function to re-read the rasters internally, so the DataLoader is independent of the env_layers dict loaded above.

Code 
dl_train, dl_val, dl_test = make_dataloaders(
    layer_paths=LAYER_PATHS,
    window_size=WINDOW_SIZE,
    batch_size=BATCH_SIZE,
    train_split=0.8,
    val_split=0.1,
    scalar_cols=SCALAR_COLS,
    df=step_df,
)
print(f"Train batches : {len(dl_train)}")
print(f"Val   batches : {len(dl_val)}")
print(f"Test  batches : {len(dl_test)}")

Inspect one batch to verify tensor shapes match ModelParams expectations

x1 has one channel per spatial band (NDVI + NDWI + NDMI = 3 with the index raster). The scalar covariates in x2 are broadcast to full H × W maps inside ConvJointModel and concatenated with x1 there, giving the CNN N_SPATIAL_CHANNELS + len(SCALAR_COLS) = 3 + 5 = 8 input channels total.

The px2 and py2 are the target that the model is trying to predict, and are the pixel values of the next step (with the centre cell being (50, 50))

next(iter(dl_train)) will call the next batch, which are randomly shuffled, so calling the function again will provide different training samples.

ModelParams

A thin dict-like container (it is a wrapper around something else rather than storing data) that groups all architecture hyper-parameters so they can be passed to ConvJointModel and logged together.

This is where the parameters that are passed to the model are set.

Code 
params = ModelParams({

    "image_dim":                 WINDOW_SIZE,           # spatial window size (pixels)
    "pixel_size":                PIXEL_SIZE,            # metres per pixel
    "dim_in_nonspatial_to_grid": len(SCALAR_COLS),      # scalar cols tiled into window

    "dense_dim_hidden":          64,                    # hidden units in the scalar MLP

    "padding":                   1,                     # same-padding preserves spatial

ConvJointModel

The deepSSF model! A joint habitat–movement model with two heads: 1. Habitat head — a small CNN applied to the spatial window (env layers + tiled scalars) that outputs a per-pixel log-suitability map. 2. Movement head — a dense MLP (fully-connected layer) that takes the scalar covariates and the previous bearing, and produces parameters for a parametric movement kernel (a mixture of wrapped distributions centred on the current location).

The two log-probability surfaces are summed pixel-wise to give the joint predicted probability map for the animal’s next step.

Code 
model = ConvJointModel(params).to(DEVICE)
n_params = sum(p.numel() for p in model.parameters())
print(f"Model parameters : {n_params:,}")

negativeLogLikeLoss

Scores each predicted probability map against the true next-step pixel index; minimising it pushes probability mass toward observed locations.

Code 
loss_fn = negativeLogLikeLoss(reduction="mean")

make_optimisers()

Creates two Adam optimisers with separate learning rates:

  • lr_habitat
    • controls the CNN (habitat) head
  • lr_movement
    • controls the movement branch (conv_movement + fcn_movement_all), kept lower for stability

It also returns a ReduceLROnPlateau scheduler for each optimiser that reduces the learning rate by a factor of scheduler_factor (default = 0.1) if that head’s validation loss does not improve for scheduler_patience epochs (default = 5).

Note that each scheduler now watches its own component of the validation loss. Previously both watched the combined loss, which is dominated by the movement component — so the movement head’s plateau was what cut the habitat learning rate. With that fixed, the two learning rates no longer have to be separated by two orders of magnitude to stop movement from running away with training; start closer together and tune from there.

Code 
optimisers, schedulers = make_optimisers(
    model, lr_habitat=1e-4, lr_movement=1e-5, scheduler_patience=3, scheduler_factor=0.5
)

EarlyStopping

Monitors validation loss and saves the best model weights to disk whenever a new minimum is reached. Training stops automatically if the loss does not improve for patience consecutive epochs.

monitor="both" — when to stop

The combined loss is habitat + movement + logZ, and because the movement surface is sharply peaked on the central pixels (animals mostly stay put between steps) it improves by far more over a run than the diffuse habitat surface does — roughly 1.2 nats against 0.05. Habitat’s improvement therefore sits inside movement’s epoch-to-epoch noise, and monitoring the combined loss alone ends the run on movement’s schedule while habitat is still learning. With monitor="both" each component keeps its own patience budget and training stops only once both have plateaued.

checkpoint_on — when to save

logZ = logsumexp(habitat + movement) is the normaliser of the joint surface. Both surfaces arrive already normalised over the window, so it is the log of

Z = sum over cells of  p_habitat(cell) * p_movement(cell)

— the overlap between the two, i.e. the average habitat probability weighted by where the movement kernel says the animal could actually go. A flat habitat surface gives Z = 1/(H*W), hence logZ = -log(H*W) = -8.64 for a 75 px window — which is why an untrained model reports total ≈ movement almost exactly: the uniform habitat term and the normaliser cancel.

logZ is what makes this a step selection likelihood rather than a plain habitat model. But it also means the combined loss is not monotone in the habitat loss. In the habitat-only stage of the run below, movement is pinned and yet:

epoch combined habitat movement
11 4.1155 8.5162 4.1268
12 4.1156 8.4817 4.1268
…
20 4.1050 8.5781 4.1268

The combined loss falls every epoch, so a checkpoint is written every epoch — but habitat was at its best back at epoch 12 and is getting worse.

Why, given the filters apply the same operation everywhere?

They do — conv_habitat is four Conv2d layers with no positional input (the scalar covariates are broadcast to constant layers), so it is translation-equivariant: identical covariates get an identical value wherever they sit in the window. It cannot single out “near the pig”.

What differs is the availability set each criterion contrasts the used cell against. Writing p_habitat = softmax(f), the habitat gradients are

combined :  E_q[df/dθ]        - df(y)/dθ      q = p_habitat * p_movement / Z
habitat  :  E_p_habitat[df/dθ] - df(y)/dθ

Both raise f at the observed cell and lower it at cells drawn from an availability distribution — pure operations in covariate space. Only the distribution differs:

available ~ effective cells (of 5625) mean covariate distance from used cell
q — the reachable set 109 0.026
p_habitat — the whole window 5460 0.059

So the combined loss asks the filters to separate the chosen cell from near-identical neighbours; the habitat loss asks them to separate it from the whole 1500 m window. Filters tuned for one are not the filters that win the other. logZ falling is a symptom of sharpened local discrimination — one chosen cell up, its ~108 unchosen neighbours down — not a loophole.

Which criterion you want is a genuine choice:

  • checkpoint_on="total" (default) saves the best joint step-selection model, with habitat fitted against availability. This is the classical iSSF estimand, and the right one if the habitat surface will be mapped as a selection surface with predict_habitat_landscape().
  • checkpoint_on="active" keys the checkpoint on whichever head is training during a single-head stage. It answers a different, RSF-flavoured question — which surface best predicts used locations against uniform availability over the window — which makes it most useful as a diagnostic of whether the habitat head is learning at all.

Keep the magnitudes in view: habitat here sits only ~0.04–0.15 nats below a uniform surface while movement is ~4.4 nats below it, so this choice moves a component worth a few percent of the model’s predictive power.

head_paths — keeping both

Checkpoints always hold the whole model — the heads are not stored separately. head_paths writes an extra file per head, each a complete model, captured at the epoch where that head’s own loss was lowest, tracked across the entire run. load_head_weights() then copies just one head’s weights out of such a file.

An untrained habitat surface is uniform over the window, so its baseline should land near log(75 * 75) = 8.635; the gap between that and the final val_habitat_losses is a direct read on how much the habitat head actually learned.

Staged training

stages runs the two sub-networks as a coordinate ascent on the same joint likelihood, rather than reweighting it:

  1. movement only — get a sensible availability kernel in place first, since habitat is fitted conditional on it
  2. habitat only — habitat now runs to its own convergence, on its own early-stopping clock, with the movement surface held fixed in the likelihood as an offset
  3. both — a joint pass to settle

A frozen sub-network keeps contributing its surface to the loss; only its weights stop moving. This is why staging is used instead of negativeLogLikeLoss(freeze_movement=True) — that flag drops the movement surface from the combined loss, so habitat would have to explain the movement structure too and would learn a distance-decay bump centred on the previous location, which is the opposite of a clean resource-selection surface.

Early stopping ends the current stage and advances to the next, so the final stage’s early stop ends the run.

Every epoch, a plot of the training and validation loss, and the predicted probability maps (movement, habitat selection and next-step) are written to SNAPSHOT_DIR, which will be turned into a GIF in the next cell.

Choosing which checkpoint to use

fit() leaves the model holding its final-epoch weights, not the best ones, so load a checkpoint before testing or simulating.

  • best_model.pt — the model to use for simulation. Both heads from one epoch, so the joint likelihood is the one that was actually measured.
  • best_model_habitat.pt / best_model_movement.pt — each head at its own best epoch, tracked across the whole run.

Mixing them is a deliberate trade: taking the habitat head from a different epoch gives the sharpest habitat surface to map, but the two heads then come from different epochs and the joint model’s likelihood is no longer what either checkpoint recorded. Use it for the landscape predictions below, not for simulating trajectories.

Habitat selection across the full landscape

predict_habitat_landscape()

Everything so far has run the model on a WINDOW_SIZE crop centred on the animal. But the habitat sub-network is fully convolutional — four 3x3 convolutions with stride 1 and padding 1, no pooling and no dense layer — so the same trained filters can be swept across the entire raster in a single pass. Convolution is translation-equivariant, so the value at a pixel is exactly what the model would have produced for a window centred on that pixel.

That gives a landscape-wide habitat selection surface. Read it as a relative ranking of cells: “if the animal were somewhere on this landscape, how attractive is each cell”. It deliberately says nothing about whether the animal could reach a cell in one step — that constraint lives in the movement kernel, which takes no part here. The two are only combined over a local window, which is what simulate_next_step() does.

  • Inputs:
    • model
      • the trained model; only model.conv_habitat is used
    • landscape_rasters
      • the spatial covariates as a list of 2-D tensors, in the same order and on the same scaling as training — i.e. exactly what get_landscape() returns
    • scalars
      • the scalar covariates for the moment being predicted, in SCALAR_COLS order. make_simulation_inputs() builds this row for us, so the encoding cannot drift from what the simulation uses. Each value is broadcast to a constant layer covering the whole landscape (the same thing Scalar_to_Grid_Block does for a window — that block can’t be reused here because its output size is fixed to WINDOW_SIZE)
    • normalise
      • subtract the log-sum-exp over the whole landscape, making the surface a log-probability that sums to 1 across all valid cells
    • edge_buffer
      • how many border pixels to mask as NaN. Defaults to habitat_edge_buffer(model) — the exact width the zero-padding reaches, 1 pixel per conv layer, so 4 here. Those pixels saw padding rather than landscape and are not comparable with the interior
    • chunk_rows
      • process this many raster rows at a time. A full-landscape activation is several hundred MB, enough to exhaust a GPU; the chunks overlap by edge_buffer so the result is identical to a single pass
  • Outputs: a [height, width] NumPy array of log-probabilities, NaN in the border. Take np.exp() for probabilities.

Save the hourly habitat selection surfaces as a raster (TIF)

Writing them out with the raster’s transform and CRS means they can be opened directly in QGIS/ArcGIS or read back with rasterio, and overlaid on the other layers in mapping/.

One band per hour rather than one file per hour: the 24 surfaces share a grid, a transform and a CRS, so a single stack keeps them together and lets GIS software step through the day with the band slider. Band n is hour n - 1 (GDAL numbers bands from 1), and each band carries its hour in both its description and its tags — so src.read(15) is 14:00.

Code 
# The CRS is not returned by load_environmental_layers(), so read it off the

# Reuses the surfaces predicted for the GIF above, so run that cell first.
# Sorting the keys rather than trusting dict insertion order means band n is
# always hour n - 1, however the surfaces were generated.
hours_sorted = sorted(hourly_surfaces)

habitat_tif = OUTPUT_DIR / f"habitat_landscape_yday{PRED_YDAY}_hourly.tif"

    habitat_tif, "w",
    driver="GTiff",
    height=height,
    width=width,

    dtype="float32",

Simulate a trajectory

simulate_trajectory()

Generates a sequence of steps by iteratively: 1. Extracting a spatial window centred on the current location. 2. Running the model to obtain a joint log-probability surface over that window. 3. Sampling the next pixel from that surface (softmax-normalised probabilities). 4. Converting the sampled pixel back to projected coordinates and advancing time.

  • Inputs:
    • model
      • the trained model
    • get_landscape
      • retrieves the landscape layers (spatial covariates) that were used to train the model
    • transform
      • raster Affine transform
    • start_x
      • x coordinate of starting location
    • start_y
      • y coordinate of starting location
    • n_steps
      • number of steps
    • starting_yday
      • starting day-of-year
    • starting_hour
      • starting hour-of-day
    • time_between_steps
      • time between steps in hours
    • window_size
      • size in pixels of the local landscape
    • month_index_fn
      • a function mapping day-of-year → month index (used by the get_landscape function). Here we are using static spatial layers so we can set it to 0.
  • Outputs: DataFrame with one row per simulated step containing:
    • x, y
      — projected coordinates of the simulated location
    • hour, yday
      — time variables updated at each step
    • month_index
      • the month index used to index the spatial variables (will be 0 if using static spatial covariates)
Code 
sim_df = simulate_trajectory(
    model,
    get_landscape=get_landscape,
    transform=raster_transform,
    start_x=start_x,
    start_y=start_y,
    n_steps=1000,

Plot with an interactive map

plot_trajectories_folium()

A static figure is fine for checking the overall shape of a trajectory, but not for asking where the animal actually went. This draws the simulated (and optionally observed) locations over a satellite basemap so you can zoom in on individual steps.

  • Inputs:
    • trajectories
      • a simulated-locations DataFrame. If it has a trajectory_id column (as simulate_trajectories() returns) each id is drawn as its own toggleable line; a plain sim_df is drawn as a single line.
    • observed
      • observed locations to overlay, e.g. step_df. Drawn as points rather than a line by default, because step_df holds 28 individuals and a single line would connect them with jumps that never happened.
    • src_crs
      • CRS of the input coordinates. Everything is reprojected to EPSG:4326 (lat/lon) for the web map — our data is in EPSG:3112.
    • basemap
      • "esri_imagery" (default), "esri_topo", "openstreetmap", or any XYZ tile-URL template. See the folium docs for more: https://python-visualization.github.io/folium/latest/user_guide/raster_layers/tiles.html
    • max_observed_points
      • observed locations are thinned to this many points. folium renders every point as its own element in the page, so all 100k+ fixes would lock up the notebook.
    • save_path
      • optionally also write a standalone HTML file.
  • Outputs: a folium.Map — leave it as the last line of a cell to display it.

folium is an optional dependency: pip install folium (or pip install "deepSSF[maps]").

Simulating many trajectories

simulate_trajectories()

Runs n_trajectories simulations and returns them stacked in one long-format DataFrame with trajectory_id and step columns.

Three methods are available:

method how it works when to use it
"batched" (default) every trajectory takes its step together, so the model sees a batch of n_trajectories windows per forward pass instead of one almost always — the forward pass is the whole cost of the simulation, and it is far better used at batch size 50 than at batch size 1
"sequential" a plain loop over simulate_trajectory() reference behaviour; needed if trajectories start at different times
"parallel" the same loop across a thread pool when start times vary and you want some overlap; the speed-up is modest (PyTorch releases the GIL inside its ops, but torch is already using several threads per op) and results are not reproducible from a seed

The one restriction on "batched" is that all trajectories share a clock, so starting_yday / starting_hour must be scalars. Start locations can still differ per trajectory — pass a list to start_x / start_y to release simulated animals from different points.

Create a heatmap of the simulated trajectories

Count the number of simulated locations per cell/pixel, with an option to discard the first n steps to reduce bias towards the initial parameters.

trajectory_heatmap()

  • Inputs
    • trajectories
      • simulated locations, as returned by simulate_trajectories() (or a list of DataFrames).
    • transform, shape
      • the landscape rasters’ affine transform and (height, width), so the heatmap grid shares their origin and CRS.
    • burn_in
      • discard the first n steps of every trajectory. Early steps cluster around the release site(s) and reflect the starting conditions rather than the fitted model.
    • agg
      • aggregate agg x agg raster pixels into one heatmap cell. At the native 20 m almost every occupied cell holds a single location, so some coarsening makes the surface readable.
  • Outputs: (counts, heatmap_transform) — an int32 array of locations per cell, and its affine transform.

The result is visualised as a PNG below, written to a GeoTIFF with save_raster() so it can be opened in QGIS, and added to the interactive map as a layer that can be toggled on and off with add_heatmap_overlay().

Code 
from deepssf import trajectory_heatmap

HEATMAP_DF   = sim_many  # trajectories to summarise (or sim_many)
BURN_IN      = 100            # drop the first n steps of every trajectory
HEATMAP_AGG  = 4              # heatmap cell = HEATMAP_AGG x HEATMAP_AGG raster pixels

heatmap, heatmap_transform = trajectory_heatmap(
    HEATMAP_DF,
    raster_transform,
    landscape_tensors[0].shape,
    burn_in=BURN_IN,
    agg=HEATMAP_AGG,
)

print(f"Heatmap grid: {heatmap.shape[0]} x {heatmap.shape[1]} cells of "
      f"{PIXEL_SIZE * HEATMAP_AGG:.0f} m")
print(f"{heatmap.sum():,} locations counted after dropping the first {BURN_IN} steps "
      f"of each trajectory")
print(f"{(heatmap > 0).sum():,} occupied cells, up to {heatmap.max():,} locations in one cell")

How much faster is "batched"?

Batching wins by more as n_trajectories grows, because a forward pass at batch size 1 leaves most of the GPU (or most of the CPU’s vector units) idle — running 50 trajectories together costs barely more per step than running one. On an Apple M-series GPU (mps), 200 steps with WINDOW_SIZE = 75:

n_trajectories "batched" "sequential" "parallel" speed-up
4 1.5 s 3.3 s 3.0 s 2.2x
16 2.0 s 14.1 s 12.1 s 6.9x
64 1.6 s 54.4 s 48.9 s 34x

Note that "parallel" is only ~10% quicker than "sequential" here: torch is already spreading each convolution across cores, so extra Python threads have little left to win. Worth re-running on your own hardware.

Code 
import time

BENCH_TRAJ, BENCH_STEPS = 100, 100

for method in ("batched", "sequential", "parallel"):
    t0 = time.perf_counter()
    _ = simulate_trajectories(
        model,
        get_landscape=get_landscape,
        transform=raster_transform,
        start_x=start_x,
        start_y=start_y,
        n_steps=BENCH_STEPS,
        n_trajectories=BENCH_TRAJ,
        method=method,
        starting_yday=test_sample["yday_t1"].iloc[0],
        starting_hour=test_sample["hour_t1"].iloc[0],
        window_size=WINDOW_SIZE,
        month_index_fn=lambda _yday: 0,
    )
    elapsed = time.perf_counter() - t0
    print(f"{method:11s} {elapsed:6.2f} s "
          f"({BENCH_TRAJ * BENCH_STEPS / elapsed:7.0f} steps/s)")
