Set script paths

These must point at the same data and rasters the model was trained on — the model takes one input channel per raster band, in LAYER_PATHS order, so a different set of layers (or a different order) either fails to load the weights or feeds the wrong covariate into each filter.

OUTPUT_DIR is the directory a training run wrote its checkpoints to, given here as a literal path rather than through get_output_dir() (which mints a new dated directory). Figures and rasters produced below are written back into the same directory, alongside the model they came from.

All-caps names below are module-level constants — set once here and referenced throughout the notebook without being reassigned. Python has no built-in constant keyword, so capitalisation is the community convention (PEP 8) to signal “do not change this value”.

Import data

The csv file is imported with a timestamp and an x and y coordinate. In our case the data was already in a projected format that is specific to Australia (EPSG:3112), which is the same crs as the raster data which will be imported.

raw_df["t1_"] = (
        pd.to_datetime(raw_df["t1_"], utc=True)

        .dt.tz_localize(None)

load_environmental_layers()

Reads each GeoTIFF listed in LAYER_PATHS, min–max

  • Scales every band to [0, 1], and returns:
    • env_layers — dict mapping layer name → NumPy array: 2-D (H × W) for single-band GeoTIFFs, 3-D (bands × H × W) for multi-band ones, where each band becomes its own model input channel
    • raster_transform — Affine object that converts pixel (row, col) indices to the projected coordinates (easting, northing) of the raster(s), which should be in the same CRS as the GPS data. This transform is used whenever we need to translate between pixel space and real-world coordinates.

Two things to watch for:

  1. The keys 's2' and 's2_dir' are reserved for the monthly Sentinel-2 composite loader — a single GeoTIFF passed under the name 's2' is silently skipped (see the note in the paths cell above).
  2. The rescaling uses a single global min/max across all bands of a file, and computes (data - lo) / hi rather than (data - lo) / (hi - lo). Our index raster is int16 scaled by 10 000 with ±10 000 fill values, so the loaded values span [0, 2] rather than [0, 1] and the three indices are not individually normalised. That is workable (the CNN can rescale internally) but if it hurts training, pre-scale each band yourself and save as .npy — non-.tif paths in LAYER_PATHS are loaded with np.load(..., mmap_mode='r') and left untouched, though at least one real .tif must remain in the dict so the transform can be set.
Code 
env_layers, raster_transform = load_environmental_layers(LAYER_PATHS)
print("Layers loaded:", list(env_layers.keys()))
for name, arr in env_layers.items():
    print(f"  {name}: shape={arr.shape}, min={arr.min():.3f}, max={arr.max():.3f}")

# Each band of a multi-band layer becomes one CNN input channel, so count bands
# (not layers) here and reuse the total when setting ModelParams below.  Deriving
# it means switching rasters in LAYER_PATHS needs no other edits.
N_SPATIAL_CHANNELS = sum(1 if arr.ndim == 2 else arr.shape[0] for arr in env_layers.values())
print(f"Spatial channels: {N_SPATIAL_CHANNELS}")

prepare_movement_df()

Converts a fixes dataframe (one row per GPS location) into a step dataframe (one row per movement between consecutive fixes).

  • For each step it computes:
    • dx, dy — displacement in projected CRS units (metres)
    • bearing — direction of travel (radians; 0 = north, clockwise positive)
    • bearing_tm1 — bearing of the previous step, used as a model input so the network can capture directional persistence by estimating a turning angle
    • dt_hour — time elapsed between consecutive fixes (hours)
    • hour_t1, yday_t1 — decimal hour-of-day and day-of-year at the step start location
    • *_sin1 / *_cos1 — sine/cosine encodings of hour and yday (see SCALAR_COLS below)

The trailing underscore on column names (x1_, y1_, t1_, etc.) flags them as “start of step” variables; x2_, y2_, t2_ are the corresponding “end of step” values, following the convention of the amt package (Signer et al. 2019). The last fix for each individual is dropped because no forward step can be formed.

Code 
# The CSV is already in amt step format, but prepare_movement_df() expects one row
# per *fix* and rebuilds the steps itself (it also derives bearing, dt_hour and the
# cyclic time encodings the model needs).  Point it at the step-start columns and
# let it re-form the steps from consecutive fixes.
step_df = prepare_movement_df(
    raw_df, 
    id_col="name", 
    time_col="t1_", 
    x_col="x1_", 
    y_col="y1_"
)
n_dropped = len(raw_df) - len(step_df)
print(f"Movement steps : {len(step_df):,}  ({n_dropped} dropped — last per individual)")

SCALAR_COLS

These are non-spatial inputs. For processing with convolutional layers, they are converted into spatial windows (rasters/arrays), and stacked with the truly spatial covariates.

The model receives a fixed-size spatial window centred on each step’s start location. To let the network express time-varying habitat preferences (e.g. different nocturnal vs diurnal use), scalar covariates are tiled into additional channels of the same H × W size, so every pixel “knows” the current time context when habitat suitability is estimated.

  • hour_t1_sin1 / hour_t1_cos1
    • Sine and cosine of (2π × hour / 24), encoding time-of-day as a circular variable. The circular encoding means 23:00 and 01:00 are treated as adjacent — a plain hour value would have an artificial discontinuity at midnight.
  • yday_t1_sin1 / yday_t1_cos1
    • Same circular encoding for day-of-year (1–365), capturing seasonal variation in habitat use (e.g. dry-season vs wet-season movements).
  • dt_hour
    • Elapsed time between consecutive fixes (hours). Because GPS collars do not always fix at a perfectly regular rate, including dt_hour lets the movement kernel rescale expected displacement proportionally to the actual time interval rather than assuming a fixed fix rate. Note: dt_hour must be supplied at simulation time as well, so that simulate_trajectory() produces inputs consistent with training.

WINDOW_SIZE

The size of the local availability window in cells/pixels - should match what was in the training script.

PIXEL_SIZE

Raster resolution in CRS units (metres here). Read straight off raster_transform rather than typed in: the transform is the authority on the grid the model is trained against, and a hand-entered value that disagrees with it silently mis-scales the movement kernel — which is parameterised in metres — against a grid measured in pixels.

Code 
# transform.a is the cell width, transform.e the (negative) cell height
PIXEL_SIZE = abs(raster_transform.a)

if not math.isclose(abs(raster_transform.a), abs(raster_transform.e)):
    raise ValueError(
        f"Non-square pixels ({abs(raster_transform.a)} x {abs(raster_transform.e)}); "
        "the model assumes square cells."
    )
print(f"Pixel size: {PIXEL_SIZE} m  →  window {WINDOW_SIZE} px = "
      f"{WINDOW_SIZE * PIXEL_SIZE:,.0f} m across")

filter_steps_by_window()

Removes steps whose straight-line displacement exceeds half the spatial window (WINDOW_SIZE × PIXEL_SIZE / 2 metres). Such steps would place the true next location outside the predicted probability map, causing an index error in the loss function.

Code 
step_df = filter_steps_by_window(
    step_df, window_size=WINDOW_SIZE, pixel_size=PIXEL_SIZE
)
print(f"Steps after window filter: {len(step_df):,}")

params_from_checkpoint()

Weights only load into a model built with the same architecture, so predicting from a trained model means reproducing its hyper-parameters exactly. Rather than re-typing the training notebook’s constants here — where a habitat branch one layer too shallow fails loudly, but a mis-set pixel_size quietly rescales the movement kernel — params_from_checkpoint() recovers them from the checkpoint and returns the ModelParams to hand to ConvJointModel.

deepssf writes the ModelParams dict into every checkpoint, so for a model trained with 0.3.1 or later it is simply read back. Older checkpoints (anything in outputs/ trained before then) do not have it, and the architecture is recovered from the layer shapes instead: a conv weight is [out_channels, in_channels, k, k] and a linear weight [out_features, in_features], which between them pin down every hyper-parameter that changes a tensor shape — input_channels, output_channels, kernel_size, both conv-layer counts, dense_dim_in_all, dense_dim_hidden and num_movement_params. Either way the result is checked against the saved tensors, so a stored params dict that contradicts its own weights raises here rather than failing later inside load_state_dict.

Three things it cannot get from the file, passed in below:

  • image_dim — the habitat branch is fully convolutional, so nothing in the weights records the training window. The movement branch’s flattened size does constrain it, and that is checked, but only to within the slack that max-pooling’s floor division allows (48–55 px all flatten to the same 288 here). WINDOW_SIZE also has to match filter_steps_by_window() above, and is the window the simulations step within.
  • pixel_size — a property of the raster, read off raster_transform.
  • device — where the model is being run, which has nothing to do with where it was trained; it defaults to this machine rather than to the recorded value.

n_scalar_covariates only fills the two ModelParams fields that no layer reads; the scalar count that matters is folded into input_channels, which comes off the weights. The check below is the one thing the checkpoint cannot do for us — that the covariates loaded in this notebook are the ones the model was trained on. It compares counts only, so keep LAYER_PATHS in the training run’s order.

Code 
params = params_from_checkpoint(
    str(CKPT_PATH),
    image_dim=WINDOW_SIZE,               # not recorded in the weights
    pixel_size=PIXEL_SIZE,               # from raster_transform
    n_scalar_covariates=len(SCALAR_COLS),
    device=DEVICE,                       # this machine, not the training machine
)
for name, value in params.to_dict().items():
    print(f"  {name:26s}: {value}")

# The covariates in this notebook must be the ones the model was trained on.
# input_channels is one channel per raster band plus one per scalar covariate,
# so a changed LAYER_PATHS or SCALAR_COLS shows up here as a count mismatch.
n_expected = N_SPATIAL_CHANNELS + len(SCALAR_COLS)
if n_expected != params.input_channels:
    raise ValueError(
        f"{N_SPATIAL_CHANNELS} raster bands + {len(SCALAR_COLS)} scalars = {n_expected} "
        f"input channels, but the checkpoint was trained with {params.input_channels}. "
        "LAYER_PATHS or SCALAR_COLS differ from the training run."
    )
print(f"\n{N_SPATIAL_CHANNELS} raster bands + {len(SCALAR_COLS)} scalars = "
      f"{params.input_channels} input channels - matches the checkpoint")

ConvJointModel

The deepSSF model! A joint habitat–movement model with two heads: 1. Habitat head — a small CNN applied to the spatial window (env layers + tiled scalars) that outputs a per-pixel log-suitability map. 2. Movement head — a dense MLP (fully-connected layer) that takes the scalar covariates and the previous bearing, and produces parameters for a parametric movement kernel (a mixture of wrapped distributions centred on the current location).

The two log-probability surfaces are summed pixel-wise to give the joint predicted probability map for the animal’s next step.

Code 
model = ConvJointModel(params).to(DEVICE)
n_params = sum(p.numel() for p in model.parameters())
print(f"Model parameters : {n_params:,}")

Load the trained model

ConvJointModel above is freshly initialised — random weights — so nothing it predicts means anything until a checkpoint is loaded into it. A training run writes three:

  • best_model.pt — the model to use for simulation. Both heads from one epoch, so the joint likelihood is the one that was actually measured.
  • best_model_habitat.pt / best_model_movement.pt — each head at its own best epoch, tracked across the whole run.

Mixing them is a deliberate trade: taking the habitat head from a different epoch gives the sharpest habitat surface to map, but the two heads then come from different epochs and the joint model’s likelihood is no longer what either checkpoint recorded. Use it for the landscape predictions below, not for simulating trajectories.

load_checkpoint() loads the weights in place and is strict about shapes, so a mismatch between the constants set above and the trained architecture raises here rather than silently predicting from a partly-random model.

Code 
# The joint model — what the simulations further down should use

print(f"                       trained with deepssf {ckpt.get('deepssf_version', 'unknown')}, "

Habitat selection across the full landscape

predict_habitat_landscape()

Everything so far has run the model on a WINDOW_SIZE crop centred on the animal. But the habitat sub-network is fully convolutional — four 3x3 convolutions with stride 1 and padding 1, no pooling and no dense layer — so the same trained filters can be swept across the entire raster in a single pass. Convolution is translation-equivariant, so the value at a pixel is exactly what the model would have produced for a window centred on that pixel.

That gives a landscape-wide habitat selection surface. Read it as a relative ranking of cells: “if the animal were somewhere on this landscape, how attractive is each cell”. It deliberately says nothing about whether the animal could reach a cell in one step — that constraint lives in the movement kernel, which takes no part here. The two are only combined over a local window, which is what simulate_next_step() does.

  • Inputs:
    • model
      • the trained model; only model.conv_habitat is used
    • landscape_rasters
      • the spatial covariates as a list of 2-D tensors, in the same order and on the same scaling as training — i.e. exactly what get_landscape() returns
    • scalars
      • the scalar covariates for the moment being predicted, in SCALAR_COLS order. make_simulation_inputs() builds this row for us, so the encoding cannot drift from what the simulation uses. Each value is broadcast to a constant layer covering the whole landscape (the same thing Scalar_to_Grid_Block does for a window — that block can’t be reused here because its output size is fixed to WINDOW_SIZE)
    • normalise
      • subtract the log-sum-exp over the whole landscape, making the surface a log-probability that sums to 1 across all valid cells
    • edge_buffer
      • how many border pixels to mask as NaN. Defaults to habitat_edge_buffer(model) — the exact width the zero-padding reaches, 1 pixel per conv layer, so 4 here. Those pixels saw padding rather than landscape and are not comparable with the interior
    • chunk_rows
      • process this many raster rows at a time. A full-landscape activation is several hundred MB, enough to exhaust a GPU; the chunks overlap by edge_buffer so the result is identical to a single pass
  • Outputs: a [height, width] NumPy array of log-probabilities, NaN in the border. Take np.exp() for probabilities.
Code 
from deepssf import (
    habitat_edge_buffer,
    make_simulation_inputs,
    predict_habitat_landscape,
)

# Predict for one moment in time: 2 am on day 200.  make_simulation_inputs
# returns one row per step, so ask for a single step and take row 0 — that
# guarantees the sin/cos encoding matches what the simulation feeds the model.

    n_steps=1, starting_yday=PRED_YDAY, starting_hour=PRED_HOUR

print(f"scalar covariates ({', '.join(SCALAR_COLS)}):\n  {scalars_pred}")

habitat_log = predict_habitat_landscape(
    model,
    landscape_rasters=get_landscape(0),   # static layers → month index 0
    scalars=scalars_pred,
)
print(f"\nSurface {habitat_log.shape}, masked border "
      f"{habitat_edge_buffer(model)} px")
print(f"log-probability range: {np.nanmin(habitat_log):.2f} to "
      f"{np.nanmax(habitat_log):.2f}")
print(f"probabilities sum to  : {np.nansum(np.exp(habitat_log)):.4f}")

How does habitat selection change through the day?

The scalar covariates are inputs to the habitat CNN, so the same landscape produces a different surface at different times of day. Re-running the prediction at different times of day shows what the model has learned.

Each surface is normalised over the landscape independently, so the panels show where selection is concentrated at that hour, not the overall level of activity.

These surfaces only show the habitat selection, and not where would expect to find pigs, as these maps do not take movement into consideration. To generate distribution maps we need to simulate movement trajectories.

Code 
PRED_HOURS = [0, 6, 12, 18]

fig, axes = plt.subplots(2, 2, figsize=(13, 10))
surfaces = {}
for ax, hour in zip(axes.flat, PRED_HOURS, strict=True):
    scalars_h = make_simulation_inputs(
        n_steps=1, starting_yday=PRED_YDAY, starting_hour=float(hour)
    )[0][0]
    surf = predict_habitat_landscape(
        model, landscape_rasters=get_landscape(0), scalars=scalars_h
    )
    surfaces[hour] = surf

    lo, hi = np.nanpercentile(surf, [1, 99.9])
    rasterio.plot.show(
        surf, transform=raster_transform, ax=ax, cmap="viridis", vmin=lo, vmax=hi
    )
    ax.set_title(f"{hour:02d}:00")
    ax.set_xlabel("Easting (m)")
    ax.set_ylabel("Northing (m)")

Simulate a trajectory

simulate_trajectory()

Generates a sequence of steps by iteratively: 1. Extracting a spatial window centred on the current location. 2. Running the model to obtain a joint log-probability surface over that window. 3. Sampling the next pixel from that surface (softmax-normalised probabilities). 4. Converting the sampled pixel back to projected coordinates and advancing time.

  • Inputs:
    • model
      • the trained model
    • get_landscape
      • retrieves the landscape layers (spatial covariates) that were used to train the model
    • transform
      • raster Affine transform
    • start_x
      • x coordinate of starting location
    • start_y
      • y coordinate of starting location
    • n_steps
      • number of steps
    • starting_yday
      • starting day-of-year
    • starting_hour
      • starting hour-of-day
    • time_between_steps
      • time between steps in hours
    • window_size
      • size in pixels of the local landscape
    • month_index_fn
      • a function mapping day-of-year → month index (used by the get_landscape function). Here we are using static spatial layers so we can set it to 0.
  • Outputs: DataFrame with one row per simulated step containing:
    • x, y
      — projected coordinates of the simulated location
    • hour, yday
      — time variables updated at each step
    • month_index
      • the month index used to index the spatial variables (will be 0 if using static spatial covariates)

Plot with an interactive map

plot_trajectories_folium()

A static figure is fine for checking the overall shape of a trajectory, but not for asking where the animal actually went. This draws the simulated (and optionally observed) locations over a satellite basemap so you can zoom in on individual steps.

  • Inputs:
    • trajectories

Simulating many trajectories

simulate_trajectories()

Runs n_trajectories simulations and returns them stacked in one long-format DataFrame with trajectory_id and step columns.

Three methods are available:

method how it works when to use it
"batched" (default) every trajectory takes its step together, so the model sees a batch of n_trajectories windows per forward pass instead of one almost always — the forward pass is the whole cost of the simulation, and it is far better used at batch size 50 than at batch size 1
"sequential" a plain loop over simulate_trajectory() reference behaviour; needed if trajectories start at different times
"parallel" the same loop across a thread pool when start times vary and you want some overlap; the speed-up is modest (PyTorch releases the GIL inside its ops, but torch is already using several threads per op) and results are not reproducible from a seed

The one restriction on "batched" is that all trajectories share a clock, so starting_yday / starting_hour must be scalars. Start locations can still differ per trajectory — pass a list to start_x / start_y to release simulated animals from different points.

Create a heatmap of the simulated trajectories

Count the number of simulated locations per cell/pixel, with an option to discard the first n steps to reduce bias towards the initial parameters.

trajectory_heatmap()

  • Inputs
    • trajectories
      • simulated locations, as returned by simulate_trajectories() (or a list of DataFrames).
    • transform, shape
      • the landscape rasters’ affine transform and (height, width), so the heatmap grid shares their origin and CRS.
    • burn_in
      • discard the first n steps of every trajectory. Early steps cluster around the release site(s) and reflect the starting conditions rather than the fitted model.
    • agg
      • aggregate agg x agg raster pixels into one heatmap cell. At the native 20 m almost every occupied cell holds a single location, so some coarsening makes the surface readable.
  • Outputs: (counts, heatmap_transform) — an int32 array of locations per cell, and its affine transform.

HEATMAP_PERIOD selects which part of the year the counts come from: "full" uses every simulated location, "wet" and "dry" keep only those whose day-of-year falls in the November–April wet season or the May–October dry season. The period is filtered before trajectory_heatmap() is called and named in the output filenames, so the three surfaces can be written side by side.

The result is visualised as a PNG below, written to a GeoTIFF with save_raster() so it can be opened in QGIS, and added to the interactive map as a layer that can be toggled on and off with add_heatmap_overlay().

HEATMAP_DF     = sim_scattered  # trajectories to summarise (or sim_many)
BURN_IN        = 0              # drop the first n steps of every trajectory
HEATMAP_AGG    = 2              # heatmap cell = HEATMAP_AGG x HEATMAP_AGG raster pixels
HEATMAP_PERIOD = "full"         # "full", "wet" or "dry" — which part of the year to count

# Day-of-year bounds of the monsoonal seasons in the Top End: the wet runs
# November to April, the dry May to October.  The wet range wraps through New
# Year (305 > 120), which is why the filter below splits on start <= end.
SEASON_YDAYS = {
    "wet": (305, 120),   # 1 Nov - 30 Apr
    "dry": (121, 304),   # 1 May - 31 Oct
}


def filter_period(df, period):
    """Subset simulated locations to one season, using the simulated yday."""
    if period == "full":
        return df
    if period not in SEASON_YDAYS:
        raise ValueError(
            f"period must be 'full', 'wet' or 'dry', got {period!r}"
        )
    start, end = SEASON_YDAYS[period]
    # Floor to the calendar day: yday is fractional within a step (283.5 is
    # midday on day 283), and comparing the raw value would drop the steps
    # falling between the last day of one season and the first of the next.
    yday = np.floor(df["yday"])
    in_season = (
        yday.between(start, end) if start <= end else (yday >= start) | (yday <= end)
    )
    return df[in_season]


heatmap_df = filter_period(HEATMAP_DF, HEATMAP_PERIOD)
if heatmap_df.empty:
    raise ValueError(
        f"no simulated locations fall in the {HEATMAP_PERIOD} season — the "
        f"simulation spans yday {HEATMAP_DF['yday'].min():.0f} to "
        f"{HEATMAP_DF['yday'].max():.0f}"
    )

# Reused by the plot, GeoTIFF and web map below so they all describe the same
# subset: the number of trajectories that actually contribute locations, and a
# filename suffix naming the period.
N_HEATMAP_TRAJ = heatmap_df["trajectory_id"].nunique()

Estimating landscape connectivity with betweenness

Such as from:

Bastille-Rousseau, G., Douglas-Hamilton, I., Blake, S., Northrup, J. M., & Wittemyer, G. (2018). Applying network theory to animal movements to identify properties of landscape space use. Ecological Applications: A Publication of the Ecological Society of America, 28(3), 854–864. https://doi.org/10.1002/eap.1697

and

Hofmann, D. D., Cozzi, G., McNutt, J. W., Ozgul, A., & Behr, D. M. (2023). A three-step approach for assessing landscape connectivity via simulated dispersal: African wild dog case study. Landscape Ecology, 38(4), 981–998. https://doi.org/10.1007/s10980-023-01602-4

Betweenness

Quantifies the importance of different elements of the matrix in facilitating connectivity between other patches or habitats within the landscape. It identifies key corridors or bottlenecks that serve as critical links for maintaining overall connectivity in the landscape. It is calculated as the number of times the simulated individuals enter each raster cell (which are typically aggregated to a coarser scale than the spatial covariates used in the simulations). Betweenness measures the importance of each cell within the landscape for maintaining functional connectivity

Adapted from: https://github.com/DavidDHofmann/DispersalSimulation/blob/main/AWDCaseStudy/02_Analysis/09_Betweenness.R

How it is calculated here

Following the R script, in four steps:

  1. A coarse grid of nodes. The landscape rasters are 20 m, much finer than the scale connectivity is meaningful at, so they are aggregated by BETWEENNESS_AGG into 500 m cells. Each cell is one node in the network. The grid keeps the rasters’ origin and CRS, so it lines up with the covariates and with the heatmap above.
  2. Transitions become edges. Every simulated path is walked cell by cell, and each move from one cell into the next is an edge. A trajectory contributes a given (from, to) pair once, however often it repeats it (singlecount = TRUE in the R script), so the pooled count is “how many of the simulated pigs ever made this move”, not “how many times it happened”.
  3. Edge weights invert the counts: weight = mean(count) / count. networkx reads the weight as a cost, so a transition many pigs made is cheap and shortest paths follow the routes the simulation actually took.
  4. Betweenness of a node is the number of those shortest paths running through it. Cells with high betweenness are the ones movement is funnelled through.

path_cells() and transition_counts()

  • Inputs
    • BETWEENNESS_DF
      • simulated locations, as returned by simulate_trajectories() — the same input trajectory_heatmap() takes.
    • BETWEENNESS_AGG
      • aggregate agg x agg raster pixels into one network cell. Betweenness is an all-pairs shortest path calculation, so the node count sets the runtime: 500 m cells give 3,672 nodes and about a minute, 250 m cells give 15,651 and about twenty.
    • BETWEENNESS_EPS
      • spacing, in cell widths, at which each step is densified before the cells under it are read off. Simulated steps have a median length of ~26 m but reach ~700 m, so a long step can jump clean over a 500 m cell; densifying catches it.
    • BETWEENNESS_BURN_IN, BETWEENNESS_MAX_STEPS
      • drop the first n steps of every trajectory, then keep at most m of what is left.
    • BETWEENNESS_K
      • None computes betweenness exactly; an integer estimates it from that many randomly chosen pivot nodes, which is what makes a finer grid tractable.
  • Outputs: betweenness — a float32 array on the coarsened grid, plus its affine transform bet_transform, ready for save_raster() and add_heatmap_overlay() just like the heatmap.

Betweenness is not the heatmap. The heatmap counts where the pigs were; betweenness counts the routes needed to get between places. A large open area can hold many locations and little betweenness, while a narrow crossing holds few locations and a lot of it. On the 1,000-step run the two surfaces correlate at only rho ~ 0.55 across the cells they share — related, but far from the same map. If they ever come out looking identical, something is wrong.

BETWEENNESS_MAX_STEPS matters more than it looks. Given enough steps every trajectory eventually visits most of the landscape, every adjacent pair of cells picks up an edge from nearly every trajectory, the weights flatten towards uniform, and betweenness ends up describing the grid rather than the movement. On the 599-trajectory run, the network covers 1,658 of the 3,672 cells after 1,000 steps, 3,348 after 10,000, and 3,671 — all but one — after 100,000. The R script handles this by recomputing the map at several step budgets (design$steps = c(125, 500, 2000)) and checking the pattern has settled; the same is worth doing here.

Code 
import math
import time

import networkx as nx
from rasterio.transform import Affine

BETWEENNESS_DF        = sim_scattered  # trajectories to build the network from
BETWEENNESS_AGG       = 5              # network cell = AGG x AGG raster pixels (n x 20 m)
BETWEENNESS_BURN_IN   = 0              # drop the first n steps of every trajectory
BETWEENNESS_MAX_STEPS = 10_000         # ...and keep at most this many of what is left
BETWEENNESS_PERIOD    = "full"         # "full", "wet" or "dry" — as for the heatmap
BETWEENNESS_EPS       = 0.25           # densify each step to this spacing, in cell widths
BETWEENNESS_K         = None           # None = exact; an int samples that many pivot nodes

# The network grid: the landscape rasters' origin and CRS with cells AGG times larger.
# ceil() rather than round() so the grid covers the whole raster — the same arithmetic
# trajectory_heatmap() uses, which is what makes the two grids line up cell for cell.
bet_height = math.ceil(landscape_tensors[0].shape[0] / BETWEENNESS_AGG)
bet_width  = math.ceil(landscape_tensors[0].shape[1] / BETWEENNESS_AGG)
bet_transform = raster_transform * Affine.scale(BETWEENNESS_AGG)
N_NODES = bet_height * bet_width
BET_CELL_M = PIXEL_SIZE * BETWEENNESS_AGG


def path_cells(x, y, eps=BETWEENNESS_EPS):
    """The sequence of network cells one simulated path passes through.

    Points outside the raster come back as -1 rather than being dropped, so that
    a pig which leaves the landscape and returns does not look like one long
    move between the cells either side of the excursion.
    """
    col, row = ~bet_transform * (np.asarray(x, dtype=float), np.asarray(y, dtype=float))
    if col.size < 2:
        return np.empty(0, dtype=np.int64)

    # Densify each step into enough sub-points that none can skip over a cell.
    # Most steps are far shorter than a cell and get n_sub = 1, so this costs
    # little; the occasional ~700 m step is the reason it is here at all.
    dcol, drow = np.diff(col), np.diff(row)
    n_sub = np.maximum(1, np.ceil(np.hypot(dcol, drow) / eps)).astype(np.int64)
    seg   = np.repeat(np.arange(n_sub.size), n_sub)      # step each sub-point belongs to
    start = np.repeat(np.cumsum(n_sub) - n_sub, n_sub)   # index of that step's first one
    frac  = (np.arange(n_sub.sum()) - start) / np.repeat(n_sub, n_sub)
    # Each step contributes its start and the points along it; the very last
    # location is the start of no step, so it is appended by hand.
    col_i = np.append(col[seg] + frac * dcol[seg], col[-1])
    row_i = np.append(row[seg] + frac * drow[seg], row[-1])

    c = np.floor(col_i).astype(np.int64)
    r = np.floor(row_i).astype(np.int64)
    inside = (r >= 0) & (r < bet_height) & (c >= 0) & (c < bet_width)
    node = np.where(inside, r * bet_width + c, -1)   # node ids run in raster order
    # Consecutive sub-points usually land in the same cell.  Keeping only the
    # changes leaves one entry per cell entered, and no from == to self-loops.
    return node[np.r_[True, node[1:] != node[:-1]]]


def transition_counts(df, id_col="trajectory_id"):
    """Pool cell-to-cell transitions over every trajectory.

    A trajectory contributes each (from, to) pair once however often it repeats
    it, so the counts returned are the number of *trajectories* that ever made
    each move.  Trajectories are handled one at a time rather than as a single
    array: at 599 x 100,000 locations the intermediate keys would otherwise run
    to several GB.
    """
    keys, n_edge_drops = [], 0
    for _tid, sub in df.groupby(id_col, sort=True):
        node = path_cells(sub["x"].to_numpy(), sub["y"].to_numpy())
        if node.size < 2:
            continue
        src, dst = node[:-1], node[1:]
        ok = (src >= 0) & (dst >= 0)          # drop moves touching the outside
        n_edge_drops += int((~ok).sum())
        keys.append(np.unique(src[ok] * N_NODES + dst[ok]))
    if not keys:
        raise ValueError(
            "no transitions — no trajectory entered more than one network cell"
        )
    key, count = np.unique(np.concatenate(keys), return_counts=True)
    return key // N_NODES, key % N_NODES, count, n_edge_drops


print(f"Network grid: {bet_height} x {bet_width} = {N_NODES:,} cells of {BET_CELL_M:.0f} m")

Build the network and calculate betweenness

The period filter is the same filter_period() the heatmap uses, so a betweenness surface and a heatmap built with the same PERIOD describe the same slice of the year.

Code 
bet_df = filter_period(BETWEENNESS_DF, BETWEENNESS_PERIOD)
bet_df = bet_df[
    (bet_df["step"] >= BETWEENNESS_BURN_IN)
    & (bet_df["step"] < BETWEENNESS_BURN_IN + BETWEENNESS_MAX_STEPS)
]
if bet_df.empty:
    raise ValueError(
        f"no simulated locations left — steps {BETWEENNESS_BURN_IN} to "
        f"{BETWEENNESS_BURN_IN + BETWEENNESS_MAX_STEPS} of the "
        f"{BETWEENNESS_PERIOD} season is outside what was simulated"
    )

# Reused by the plot, GeoTIFF and web map below so they all describe the same subset.
N_BET_TRAJ = bet_df["trajectory_id"].nunique()
BET_TAG = f"_{BETWEENNESS_PERIOD}"

t0 = time.time()
bet_src, bet_dst, bet_count, n_edge_drops = transition_counts(bet_df)
print(f"Period: {BETWEENNESS_PERIOD} — {len(bet_df):,} locations from {N_BET_TRAJ} "
      f"trajectories, steps {BETWEENNESS_BURN_IN} to "
      f"{BETWEENNESS_BURN_IN + BETWEENNESS_MAX_STEPS - 1}")
print(f"{len(bet_src):,} unique transitions found in {time.time() - t0:.0f} s "
      f"({n_edge_drops:,} dropped at the raster edge)")

# networkx reads the weight as a cost, so invert the counts: a transition many
# trajectories made is cheap, and shortest paths prefer it.
bet_weight = bet_count.mean() / bet_count

# Every cell is a node, including the ones no trajectory reached — they sit in the
# network isolated and score zero, as `vertices = ver` does in the R script.
bet_net = nx.DiGraph()
bet_net.add_nodes_from(range(N_NODES))
bet_net.add_weighted_edges_from(
    zip(bet_src.tolist(), bet_dst.tolist(), bet_weight.tolist(), strict=True)
)
print(f"Network: {bet_net.number_of_nodes():,} nodes, {bet_net.number_of_edges():,} edges")

t0 = time.time()
bet_scores = nx.betweenness_centrality(
    bet_net, k=BETWEENNESS_K, weight="weight", normalized=False, seed=1
)
print(f"Betweenness computed in {time.time() - t0:.0f} s"
      + ("" if BETWEENNESS_K is None else f" (approximate, {BETWEENNESS_K} pivots)"))

# Cells no trajectory ever entered are left as NaN rather than 0, so the map can
# tell them apart from cells that are in the network but on no shortest path.
in_network = np.zeros(N_NODES, dtype=bool)
in_network[bet_src] = True
in_network[bet_dst] = True
betweenness = np.full(N_NODES, np.nan, dtype=np.float32)
betweenness[in_network] = [bet_scores[n] for n in np.flatnonzero(in_network)]
betweenness = betweenness.reshape(bet_height, bet_width)

print(f"{in_network.sum():,} of {N_NODES:,} cells were entered by at least one "
      f"trajectory; betweenness runs from 0 to {np.nanmax(betweenness):,.0f}")
